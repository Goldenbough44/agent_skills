# 기획 인터뷰

사용자를 인터뷰하여 기획서를 완성한다. 기획서는 "어떻게 만들 것인가"가 아니라 "정확히 무엇을 이루고자 하는가"를 확정하는 문서이다. 수단은 개발 중에 바뀔 수 있지만, 목표는 흔들리지 않아야 한다. 그래서 이 인터뷰는 수단을 정의하지 않고 목표를 빈틈없이 규명하는 데 집중한다.

## 사용 조건

사용자가 "나를 인터뷰해"와 같이 인터뷰를 명시적으로 요청했을 때만 사용한다. 기획서를 써 달라는 요청만으로는 이 스킬을 시작하지 않는다.

## 목표와 수단의 구분

모든 질문은 던지기 전에 다음 기준으로 걸러낸다.

- 목표(질문 대상): 무엇이 존재해야 하는가, 그것이 무엇을 해내야 하는가, 어떤 결과를 주어야 하는가, 무엇이 성공인가, 무엇은 하지 않는가, 왜 해야 하는가.
- 수단(질문 대상 아님): 자료구조, 아키텍처, 프레임워크, 변수, 색상 등 구현과 표현의 세부 선택. 이는 개발·디자인 단계에서 정할 사항이다.

판단 기준은 "이 답이 달라지면 달성하려는 것이 달라지는가"이다. 달라지지 않는다면 수단이므로 묻지 않는다. 예를 들어 마지막 단계에서 버튼을 다룬다면, 어떤 버튼이 있어야 하고 각 버튼이 어떤 동작을 수행해야 하는지는 묻는다. 버튼의 색상이나 구현 프레임워크는 묻지 않는다.

사용자가 먼저 수단을 말한 경우, 그 수단으로 얻고자 하는 바를 물어 목표로 환원한다. 사용자가 그 수단 자체가 바꿀 수 없는 조건이라고 밝히면 제약 사항으로 기록한다.

## 진행 절차

### 1. 출발점 정리

첫 프롬프트와 이미 알고 있는 정보에서 확정된 것, 모호한 것, 비어 있는 것을 구분한다. 이미 답이 나온 것은 다시 묻지 않는다.

### 2. 인터뷰 계획 수립

무엇을 어떤 순서로 물을지 계획을 세운다. 계획은 숲에서 나무로 내려가는 순서를 따른다.

1. 전체 형상: 이것이 무엇인지, 왜 필요한지, 완성되었을 때의 전반적인 느낌과 모습, 성공의 기준, 범위의 경계.
2. 세부 목표: 전체 목표를 이루기 위해 달성되어야 하는 하위 목표들.
3. 원칙: 목표를 추구하는 과정에서 지켜야 할 기준과 우선순위. 개발 원칙이 아니라 기획 원칙으로, 목표를 달성하기 위해 바뀌지 않아야 할 것들.
4. 구성 요소별 스펙: 무엇이 있어야 하고 각각 무엇을 해내야 하는지.

앞 단계가 충분히 규명되기 전에는 다음 단계로 내려가지 않는다. 뒤의 질문은 앞의 답변에 의존하므로, 계획의 하위 단계는 상위 단계의 답변을 받은 뒤에 구체화한다.

계획에는 사용자가 언급한 것만 담지 않는다. 목표가 성립하려면 정해져야 하지만 사용자가 언급하지 않은 영역도 스스로 찾아 계획에 넣는다(아래 "말하지 않은 영역 찾기" 참고).

#### 인터뷰 계획 파일

계획은 머릿속에만 두지 않고 내부 작업 파일로 유지한다. 인터뷰가 길어지면 해야 했던 질문을 잊기 쉽기 때문이다.

- 인터뷰를 시작할 때 작업 디렉터리에 계획 파일을 만든다. 이 파일은 작업용이며 사용자에게 전달하지 않는다. 사용자에게는 계획 전체를 긴 목록으로 제시하지 않고, 지금 어느 부분을 다루고 있는지만 짧게 알린다.
- 파일에는 다음을 적는다: 단계별 진행 상태, 앞으로 물을 영역과 질문(숲에서 나무 순), 답변되지 않아 다시 물어야 할 질문, 확인을 기다리는 해석, 미결정으로 표시해 둔 것, 다시 확인해야 할 충돌.
- 매 질문과 답변마다 파일을 고친다. 답변된 질문은 지우고, 새로 드러난 영역과 답변에서 빠진 질문을 추가하며, 무의미해진 질문은 제거한다.
- 다음 질문은 이 파일을 확인한 뒤에 고른다.

### 3. 질문

- 한 번에 한 개만 한다. 질문을 쏟아내면 사용자는 질문에 답하느라 자신이 원래 원하던 것을 잊어버린다.
- 열린 질문으로 묻는다. 사용자가 명시적으로 요청하지 않는 한 구체적인 방안, 선택지, 예시를 먼저 제시하지 않는다. 제시된 예시는 사용자의 생각을 그쪽으로 끌어당겨 원래 의도를 흐린다. 같은 이유로 선택지를 나열하는 객관식 질문 도구를 쓰지 않고 일반 텍스트로 묻는다.
- 사용자가 원하는 것을 대신 규정하지 않는다. 추측으로 빈 곳을 채우지 않고, 답변에서 드러난 것만 확정한다.
- 확인 없이는 확정하지 않는다. 답변이 모호하거나 해석이 필요하면 이해한 바를 되물어 확인하고, 사용자가 명시적으로 확인한 뒤에만 확정한다. 이해한 바를 진술했는데 사용자가 그 부분에 답하지 않고 넘어가면, 정정이 없었다는 이유로 확정하지 않고 다시 묻는다. 확인되지 않은 해석은 기획서 파일에 적지 않는다.
- 답변에서 빠진 질문은 답을 가정하지 않는다. 여전히 필요한 질문이면 다시 묻는다.
- 지엽적인 질문을 하지 않는다. 현재 단계의 틀보다 작은 것을 미리 확정하려 하지 않는다.
- 사용자가 "모르겠다"고 답하면 선택지를 내밀지 않는다. 그 질문이 속한 상위 목표로 돌아가 다른 각도에서 묻거나, 계획 파일에 미결정으로 표시해 두고 나중에 다시 묻는다.

### 4. 말하지 않은 영역 찾기

인터뷰의 목적에는 사용자가 빠뜨렸거나 생각해 보지 못했지만 기획에 필요한 것까지 규명하는 일이 포함된다. 사용자가 말한 것만 따라가면 사용자가 떠올린 범위 안에서만 기획이 완성된다.

- 각 단계에서, 지금까지 확정된 목표가 실제로 성립하려면 무엇이 더 정해져야 하는지 스스로 점검한다. 언급되지 않은 상황, 경계 조건, 구성 요소 사이의 관계, 예외적인 경우가 대표적이다.
- 찾아낸 빈 영역은 그 영역에 대해 묻는 열린 질문으로 제시한다. 영역의 존재는 알리되 답은 제안하지 않는다.
- 이때도 목표와 수단의 구분, 숲에서 나무로 내려가는 순서, 지엽적인 질문 금지는 그대로 적용한다. 빈 영역을 찾는다는 이유로 수단이나 현재 단계보다 작은 세부를 묻지 않는다.

### 5. 답변 반영과 계획 수정

매 답변 후 다음을 수행한다.

- 확정된 내용을 기획서 파일에 반영한다(아래 "기획서 파일" 참고).
- 인터뷰 계획 파일을 고친다. 답변이 계획의 전제를 바꾸면 계획 자체를 수정한다.
- 방금 답변으로 확정한 내용을 다음 질문 전에 짧게 다시 진술한다. 파일에 반영했더라도 생략하지 않는다. 사용자가 오해를 그 자리에서 바로잡을 수 있게 하기 위함이며, 정정은 답변과 동일하게 반영한다.
- 다시 진술할 때는 사용자가 말한 그대로인 내용과 해석이 들어간 내용을 구분한다. 해석이 들어간 내용은 확정으로 진술하지 않고 확인 질문으로 묻으며, 계획 파일에 확인 대기로 적어 둔다.
- 이후 답변이 이전 답변을 흔들면 이미 한 질문이라도 다시 묻는다.
- 단계가 바뀌는 시점에는 그 단계에서 확정된 내용 전체를 짧게 요약해 사용자가 전체 그림을 놓치지 않게 한다.

### 6. 충돌 검사

언제나 목표가 원칙보다 우선한다. 새 내용이 확정될 때마다 다음을 검사한다.

- 원칙이 목표를 위반하는가.
- 원칙끼리 충돌하는가.
- 세부 목표가 상위 목표와 어긋나는가.
- 새 답변이 이전 답변과 어긋나는가.

충돌을 발견하면 임의로 해소하지 않는다. 어느 부분이 어떻게 충돌하는지 사용자에게 알리고, 어떻게 할지 다시 인터뷰한다.

### 7. 종료 조건

빈 곳 없이 목표를 99% 규명했다고 확신할 때까지 인터뷰를 멈추지 않는다. 다음을 모두 충족해야 종료한다.

- 전체 목표, 대상, 성공 기준, 범위의 안과 밖이 명확하다.
- 모든 세부 목표가 규명되었고 상위 목표와 연결된다.
- 원칙이 규명되었고, 목표 및 다른 원칙과 충돌하지 않는다.
- 모든 구성 요소에 대해 무엇이 있어야 하고 무엇을 해내야 하는지가 확정되었다.
- 사용자가 언급하지 않았지만 목표가 성립하는 데 필요한 영역까지 점검하고 규명했다.
- 인터뷰 계획 파일에 남은 질문이 없고, 확인을 기다리는 해석도 없다.
- 이 기획서만 받은 사람이 달성해야 할 바를 추가 질문 없이 이해할 수 있다.
- 사용자가 이번 기획에서 다루지 않겠다고 한 것 외에는 미결정 사항이 남아 있지 않다.

종료 조건을 채우기 위해 지엽적인 질문을 덧붙이지 않는다. 남은 빈 곳이 수단의 영역뿐이라면 규명은 끝난 것이다. 사용자가 중간에 인터뷰 종료를 요청하면 따르되, 규명되지 않은 부분은 기획서에 적지 않고 대화에서 따로 알린다.

## 기획서 파일

기획서는 인터뷰가 끝난 뒤 한 번에 쓰지 않고, 인터뷰 중에 md 파일로 만들어 계속 고쳐 나간다.

- 인터뷰를 시작할 때 report-writing 스킬을 불러와 그 기준을 지킨다.
- 확정된 내용이 처음 생기면 기획서 md 파일을 만든다. 사용자가 요청한 파일명이나 작성 형식이 있으면 그것을 따른다.
- 매 답변 후 확정된 내용을 파일에 반영한다. 답변이 바뀌거나 정정되면 해당 부분을 고쳐 쓴다. 덧붙이기만 하지 않고, 내용이 쌓이면 문서 구조도 다시 잡는다.
- 파일에는 언제나 확정된 내용만 담는다. 사용자가 명시적으로 확인하지 않은 해석, 미결정 사항, 추후 규정할 사항, 인터뷰에서 다루지 않은 영역에 대한 언급, 인터뷰 과정에 대한 서술은 적지 않는다. 이런 내용은 인터뷰 계획 파일에서 관리한다.
- 스펙은 수단을 지정하지 않고 달성해야 할 결과로 기술한다. 개발 중 구현 방식이 바뀌더라도 기획서의 문장은 그대로 유효해야 한다. 사용자가 말하지 않은 내용을 추가하지 않는다.
- 파일은 단계가 바뀌는 시점이나 사용자가 요청할 때 사용자에게 전달한다.

기획서는 다음을 포함하되, 구성은 기획 대상에 맞게 조정한다.

- 전체 목표와 배경, 대상, 성공 기준
- 범위: 포함하는 것과 포함하지 않는 것
- 세부 목표
- 원칙과 우선순위
- 구성 요소별 스펙: 존재해야 하는 것과 그것이 해내야 하는 것
- 제약 사항: 사용자가 고정 조건이라고 밝힌 것

종료 조건을 충족하면 파일 전체를 다시 읽어 확정된 내용과 어긋나는 곳이 없는지 확인한 뒤 최종본을 전달한다. 전달한 뒤 사용자가 수정을 요청하면, 수정 내용이 기존 목표나 원칙과 충돌하는지 검사하고 필요하면 인터뷰를 재개한다.
